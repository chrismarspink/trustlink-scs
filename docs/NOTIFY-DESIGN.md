# TrustLink 보안 이슈 자동 통보 — 설계안 (승인 요청)

- 문서 상태: **승인(2026-11-02)** · 구현 TrustLink 2.3.0 — 고객 통보는 VEX 발행 시에만, 내부 수신은 제품 업로드 권한자+관리자
- 승인 후 구현. 아래 "결정 필요" 4건에 답을 주면 그 내용으로 확정한다.

## 1. 목표

출시된 제품 버전의 SBOM 에서 **새 취약점이 발견되면**, 그 제품을 책임지는 내부 개발자와 그 제품을 받는 고객에게 **알맞은 시점에, 알맞은 내용으로** 자동 통보한다.

하지 않는 것:
- 취약점 판단 자동화 — 영향 여부(VEX)는 계속 개발자가 판단한다.
- 고객에게 원시 CVE 목록을 즉시 보내는 것 — 판단 전의 CVE 는 "영향 있음"으로 오해된다(2.3 참고).

## 2. 동작 개요

```
 ① 버전 등록            ② 감시                    ③ 내부 통보              ④ 판단            ⑤ 고객 통보
 SBOM 첨부  ──자동적재──▶ Dependency-Track ──새 CVE──▶ 개발자·관리자   ──▶ VEX 발행 ──▶ 그 제품 권한이 있는
 (oras/syft)            (매일 취약점 DB 갱신·재분석)   (화면 알림·메일)                   고객사 사용자(화면·메일)
```

### 2.1 ① 자동 적재 — 모든 출시 버전을 감시 대상으로

현재는 누군가 상세 화면에서 [취약점 분석 불러오기]를 눌러야 DT 프로젝트가 생긴다. 누르지 않은 버전은 감시되지 않으므로 통보도 없다.

- BFF 가 **10분마다** 레지스트리를 훑어, CycloneDX SBOM 이 붙어 있는데 DT 에 없는 `제품 @ 버전` 을 DT 에 적재한다. 기존 `ensureDTProject` 를 그대로 쓴다.
- zot 이벤트 연동 대신 주기 동기화를 택한 이유: zot 공식 이미지를 고치지 않는다는 원칙 유지, 놓친 이벤트가 없음, 구현이 단순함.
- 첫 실행 때 기존 버전(innopouch 1.0~10.0 등)이 한꺼번에 적재된다. 이때 "새 취약점" 알림이 대량으로 나오므로, **첫 적재분은 통보하지 않고 기준선으로만 기록**한다.

### 2.2 ② 감시 — Dependency-Track 의 기존 기능 사용

- DT 는 취약점 DB(NVD·GitHub 보안 권고·OSV)를 매일 갱신하고, 전체 프로젝트를 주기적으로 재분석한다. 이미 동작 중이다.
- 새로 발견된 (프로젝트, 취약점) 조합마다 DT 가 `NEW_VULNERABILITY` 알림을 낸다.
- BFF 가 기동할 때 DT 에 **알림 규칙과 웹훅 대상**을 API 로 자동 등록한다(멱등 — 이미 있으면 건드리지 않음). 관리자가 DT 화면에서 설정할 필요 없다.
- 웹훅 수신 주소는 BFF 의 **내부 전용 포트**(예: `:8089`, compose 내부망에서만 열림, 외부 포트 미공개)로 한다. DT 웹훅에는 인증 헤더를 붙일 수 없으므로 네트워크로 막는다.
- 지연: 새 CVE 공개 → DT 반영까지 보통 **수 시간 ~ 1일**. 즉시 통보는 아니다.

### 2.3 ③ 내부 통보 — 판단할 사람에게 먼저

| 항목 | 내용 |
|---|---|
| 받는 사람 | 그 제품에 **쓰기 권한**이 있는 사람(제품 권한의 업로드 대상: 기본은 `developers` 그룹) + `admins`. 자동화 계정은 제외 |
| 내용 | 제품·버전, CVE 번호, 심각도, 해당 부품(예: log4j-core 2.17.1), 상세 화면 링크("판단 필요") |
| 묶음 | 같은 제품·버전에 한 번에 여러 CVE 가 나오면 **1건으로 묶는다**(log4j 처럼 5건이 동시에 나오는 경우) |
| 중복 방지 | (제품, 버전, CVE) 당 1회만. 이미 VEX 로 판단된 CVE 는 통보하지 않음 |

### 2.4 ⑤ 고객 통보 — 판단이 끝난 뒤에

| 시점 | 내용 | 비고 |
|---|---|---|
| **VEX 발행 시 (기본)** | "innopouch 7.0 — CVE 3건 검토 완료: 영향 없음 2, 영향 있음 1(8.0 업데이트 권장)" + 상세 링크 | 고객이 받는 것은 판단 결과 |
| CRITICAL 미판단 N일 경과 시 (선택) | "innopouch 7.0 — 심각 취약점 1건 조사 중" | 판단이 늦어질 때 고객이 먼저 듣는 일을 막음 |

- 받는 사람: 그 제품에 **읽기 권한이 있는 고객사의 사용자** + 그 고객사의 **보안 통보 주소**(`관리 › 고객사`, 계정 없이 메일만 받는 주소, v2.5.0). 외부 사용자는 이메일 필수(v2.5.0). 기존 제품 권한 데이터(`canAccess`)를 그대로 쓰므로 **권한 없는 고객에게는 절대 가지 않는다**.
- 고객에게는 공개 CVE 번호와 판단 결과만 보낸다. 내부 코멘트는 보내지 않는다.

### 2.5 받는 사람별 내용 차이

| 항목 | 내부 개발자·관리자 | 고객 |
|---|---|---|
| 목적 | 판단하라(할 일) | 판단 결과와 조치(알림) |
| 시점 | 새 CVE 발견 즉시 | VEX 발행 시 |
| 제품 범위 | 쓰기 권한이 있는 모든 제품 | 읽기 권한이 있는 제품만 |
| CVE | 번호·심각도·CVSS·EPSS·참고 링크 | 번호·심각도 |
| 부품 | 부품명·버전·위치(어느 SBOM) | 기본은 표시 안 함(필요 시 부품명만) |
| 판단 | 미판단 상태, 판단 화면 링크 | 영향 없음 / 영향 있음 / 수정됨 / 조사 중 + 근거 요약 |
| 조치 | "VEX 발행 필요", 기한 | 업데이트 권장 버전, 완화 방법 |
| 내부 정보 | 개발자 코멘트, DT 분석 내역 | **제외**(코멘트·내부 경로·담당자) |
| 링크 | 상세 화면 › 취약점 분석 | 상세 화면(VEX 보기), VEX 파일 받기 |

## 3. 통보 수단

| 수단 | 대상 | 필요한 것 | 단계 |
|---|---|---|---|
| **화면 알림** (상단 종 아이콘, 읽음 표시) | 모두 | 없음 | 1 |
| **이메일** | 모두 | 회사 메일 서버(SMTP) 주소·계정. 받는 주소는 Keycloak 사용자 이메일 | 2 |
| 사내 메신저 웹훅 (Slack·Teams 등) | 내부 | 웹훅 URL | 선택 |
| 고객 시스템 웹훅 | 고객사 | 고객사별 URL | 선택(후속) |

- 사용자별 수신 설정: 이메일 끄기·켜기(화면 알림은 항상).
- 이메일은 **하루 1회 묶음** 또는 즉시 중 관리자가 고른다(기본: 내부는 즉시, 고객은 VEX 발행 시 즉시).

## 4. 관리 화면 · 기록

- `관리 › 통보` 화면: 최근 통보 목록(언제·무엇을·누구에게·성공/실패), 실패한 메일 재발송, 메일 서버 연결 시험 버튼.
- 모든 통보는 기존 감사 기록(`/var/lib/trustlink/sor.jsonl`)에 남긴다.
- 통보 상태(보낸 것·읽음)는 BFF 데이터 볼륨에 파일로 저장한다(외부 DB 추가 없음, 기존 세션·권한 저장 방식과 같음).

## 5. 구현 단계와 일정

| 단계 | 내용 | 예상 |
|---|---|---|
| 1 | 자동 적재(10분 주기, 기준선) · DT 알림 규칙/웹훅 자동 등록 · 내부 수신 포트 · 화면 알림(내부) · 관리 › 통보 | 2일 |
| 2 | 이메일 발송(SMTP, 묶음·재시도) · 사용자 수신 설정 | 1~1.5일 |
| 3 | VEX 발행 시 고객 통보(화면·메일) | 1일 |
| 선택 | CRITICAL 미판단 N일 사전 통보 · 사내 메신저 · 고객 웹훅 | 각 0.5~1일 |

단계별로 배포·시험하고, 매뉴얼(v2.3)에 관리자 설정·사용자 수신 설정·시험 항목을 추가한다.

## 6. 시험 방법

1. **실제 탐지**: 알려진 취약 부품(예: log4j-core 2.14.1, CVE-2021-44228)이 든 SBOM 을 `products/sandbox` 에 올린다 → 10분 안에 DT 적재 → 내부 개발자에게 화면 알림·메일 도착 확인.
2. **새 CVE 시뮬레이션**: DT 알림 형식의 가짜 웹훅을 내부 포트로 보내 묶음·중복 방지·권한 필터를 확인한다(단위 시험 포함).
3. **고객 범위**: acme1(innopouch 권한)은 innopouch 통보만, partner1(권한 없음)은 아무것도 받지 않는지 확인.
4. **외부 차단**: 공개 포트(28080)에서 웹훅 주소로 요청하면 404 인지 확인.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 알림 폭주(기존 버전 첫 적재, 대형 CVE) | 첫 적재는 기준선만 기록, 제품·버전 단위 묶음, 하루 묶음 옵션 |
| 오탐이 고객에게 감 | 고객 통보는 VEX 발행 시에만(기본) |
| 메일 실패 | 재시도 3회, 관리 화면에 실패 표시·재발송 |
| 웹훅 위조 | 내부 전용 포트, 외부 포트에는 경로 미등록 |
| SBOM 교체가 DT 에 반영 안 됨(현행 동작) | 새 SBOM 첨부를 감지하면 DT 에 재적재(1단계에 포함) |

## 8. 결정 필요

1. **고객 통보 시점**: VEX 발행 시에만(권장) / + CRITICAL 미판단 N일 사전 통보(N=?)
2. **이메일 사용 여부와 SMTP 정보**: 사용 시 메일 서버 주소·포트·계정·보내는 주소. 미정이면 1단계(화면 알림)부터 진행
3. **내부 받는 사람**: 제품 쓰기 권한자 + 관리자(권장) / 관리자만 / 별도 지정 담당자
4. **사내 메신저 연동**: 필요 시 종류(Slack·Teams 등)와 웹훅 URL
