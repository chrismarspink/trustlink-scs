# 취약점 DB 피드 허브

취약점 DB(NVD·OSV·KEV·EPSS 등 21종) 수집을 TrustLink 설치마다 하지 않고 **한 곳(허브)** 에서 하고,
여러 설치가 그 허브에서 받아 쓰게 하는 구성입니다. 켜지 않으면 기존 동작은 그대로입니다.

## 구성

```
 원본 사이트(NVD, OSV, …)
        │  매일 접속 창 안에서만
        ▼
 ┌────────────────┐   서명된 스냅샷 + 파일      ┌──────────────────────────┐
 │  피드 허브      │ ─────────────────────────▶ │ 설치 A (자사)  vuln-mirror │──▶ Dependency-Track
 │  feed-hub      │   구독 키로 읽기            └──────────────────────────┘
 │  (수집·서명)    │ ─────────────────────────▶   설치 B (고객사)  vuln-mirror
 └────────────────┘ ─────────────────────────▶   DMZ 미러 ──▶ 폐쇄망 미러
        │
        └─ export ──▶ 번들(tar) ──(매체 반입)──▶ 완전 폐쇄망 설치: import
```

- 받는 쪽이 가져갑니다. 허브가 설치 안으로 들어가지 않으므로, 받는 쪽 방화벽은 **허브 한 곳으로 나가는 방향**만 열면 됩니다.
- 설치 안의 `vuln-mirror` 는 그대로 남습니다. 원본 사이트 대신 허브에서 받을 뿐이고, Dependency-Track 등은 지금처럼 설치 안의 미러를 봅니다.
- 허브와 설치의 `vuln-mirror` 는 같은 이미지·같은 프로그램입니다(`trustlink-admin mirror`). 허브는 `MIRROR_HUB=1` 로 띄운 것입니다.

## 받는 환경 세 가지

| 환경 | 받는 방법 | 설정 |
|---|---|---|
| 인터넷(또는 허브)에 나갈 수 있는 설치 | 접속 창 안에서 허브에 접속 | 상위 미러 = 허브 주소, 허브 공개키, 구독 키 |
| DMZ → 폐쇄망 | DMZ 미러가 허브에서 받고, 폐쇄망 미러가 DMZ 미러에서 받음 | 기존 "상위 미러" 연쇄 그대로. DMZ 미러도 서명하게 하려면 DMZ 미러를 허브 모드로 |
| 완전 폐쇄망 | 허브에서 번들(tar)을 내보내 매체로 반입 | `mirror import` (아래) |

## 무엇을 확인하는가

- **구독 키**: 허브는 키가 없는 읽기를 401 로 거부합니다. 허브에는 키의 SHA-256 만 저장하고, 키는 발급할 때 한 번만 보여 줍니다.
- **서명**: 허브는 파일 목록(경로·크기·SHA-256)과 스냅샷 ID, 생성 시각을 Ed25519 로 서명합니다. 받는 쪽은 허브 공개키로 검증합니다.
- **파일 해시**: 받은 파일의 SHA-256 이 서명된 목록과 다르면 교체하지 않습니다. 기존 사본이 그대로 남습니다.
- **되돌리기 방지**: 같은 허브 키로 이미 받아들인 것보다 오래된 스냅샷은 거부합니다.
- **스냅샷 ID**: 받는 쪽 스냅샷 ID 가 허브와 같으면 같은 DB 내용입니다. "그날 어떤 DB 로 판정했는가"를 허브 기준으로 맞춰 볼 수 있습니다.

받는 쪽에 허브 공개키를 넣지 않으면 검증 없이 받습니다(기존 상위 미러 동작). 화면에 "검증하지 않고 받습니다"라고 표시됩니다.

## 허브 띄우기

```sh
cd feed-hub
docker compose up -d
docker compose exec feed-hub trustlink-admin mirror pubkey        # 받는 쪽에 넣을 공개키
docker compose exec feed-hub trustlink-admin mirror sub add site-a # 구독 키 발급(한 번만 표시)
docker compose exec feed-hub trustlink-admin mirror sub list       # 구독자와 마지막 접속 시각
docker compose exec feed-hub trustlink-admin mirror sub rm site-a  # 구독 해지
```

- 기본으로 매일 02:00~06:00(KST)에 21종 전부를 받습니다. 디스크는 10~15GB 를 쓰고, 여유가 20GB 아래면 받지 않습니다.
- 포트는 기본으로 서버 안(127.0.0.1:8090)에만 엽니다. 다른 서버가 받게 하려면 **HTTPS 프록시 뒤에** 두세요. 구독 키가 요청 헤더(`X-Mirror-Sub`)로 오가므로 평문 HTTP 로 밖에 열면 안 됩니다.
- 접속 창·출처를 바꾸려면 `PUT /_api/policy` 를 관리 키(`X-Mirror-Key`, 볼륨의 `_state/api.key`)로 부릅니다. 허브에는 관리 화면이 없습니다.
- 서명 키는 볼륨의 `_state/sign.key` 입니다. 볼륨을 잃으면 공개키가 바뀌므로 받는 쪽 설정도 바꿔야 합니다. 백업 대상에 넣으세요.

## 받는 쪽 설정 (TrustLink 설치)

관리 콘솔 › 취약점 DB 미러 › 접속 정책에서:

1. 접속 정책을 "정기 접속"으로, 접속 창은 **허브의 접속 창이 끝난 뒤**로 잡습니다(예: 허브 02~06시, 받는 쪽 06~08시).
2. 상위 미러에 허브 주소(`https://hub.example.com`)를 넣습니다.
3. 허브 공개키와 구독 키를 넣고 저장합니다.

구독 키는 미러 볼륨의 `_state/upstream.key` 에만 저장됩니다. 정책 파일, 상태 응답, 원장에는 남지 않고, 화면에는 "저장됨"으로만 보입니다.
저장 뒤 화면 아래에 "마지막으로 서명을 확인해 받아들인 허브 스냅샷"이 표시되면 검증이 되고 있는 것입니다.

## 완전 폐쇄망: 번들

허브에서 내보내기(허브가 DB 를 받는 중이 아닐 때):

```sh
cd feed-hub
docker compose run --rm -v "$PWD/out:/out" feed-hub mirror export /out/vulndb-$(date +%Y%m%d).tar
```

폐쇄망 설치에서 들여오기. 미러를 멈춘 상태에서 합니다(실행 중인 미러는 메모리의 목록으로 덮어씁니다):

```sh
docker compose stop vuln-mirror
docker compose run --rm -v /반입/경로:/bundle -e MIRROR_PUBKEY='<허브 공개키>' vuln-mirror mirror import /bundle/vulndb-20261127.tar
docker compose start vuln-mirror
```

- 서명이 맞지 않거나, 파일 하나라도 해시가 다르거나, 번들이 불완전하면 목록을 바꾸지 않고 끝냅니다.
- 번들은 전체 스냅샷입니다. 이미 같은 내용인 파일은 다시 쓰지 않고, 번들에 없는 파일은 지웁니다.
- 공개키를 관리 화면에 저장해 두었다면 `-e MIRROR_PUBKEY` 는 생략할 수 있습니다.

## 알아 둘 점

- **재배포 조건을 먼저 확인하세요.** 허브는 공개 DB 를 다시 내주는 것이므로, 자사 설치 밖(고객)에 열기 전에 출처별 이용 조건을 확인해야 합니다. 그 전에는 자사 설치 전용으로 쓰는 것을 권합니다.
- 허브가 DB 를 받는 도중에 받는 쪽이 접속하면, 목록과 파일이 잠깐 어긋나 그 출처만 오류로 끝날 수 있습니다. 한 시간 뒤 자동으로 다시 시도합니다. 접속 창을 겹치지 않게 잡으면 생기지 않습니다.
- 허브 모드 미러는 키 없는 읽기를 거부하므로 Dependency-Track 이 직접 볼 수 없습니다. 설치 안의 `vuln-mirror` 를 허브 모드로 바꾸지 마세요. 허브는 따로 띄웁니다.
- 받을 때마다 전체 목록을 대조하지만 내려받는 것은 바뀐 파일뿐입니다(ETag·수정 시각 조건부 요청). 별도의 델타 형식은 없습니다.
- 서명 키 교체(회전) 절차와 구독자별 출처 제한은 아직 없습니다.
- 규제 카탈로그는 아직 허브로 옮기지 않았습니다.
